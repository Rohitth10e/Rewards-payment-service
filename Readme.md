# Rewards Payment Service

An educational Spring Boot service that accepts reward-payment requests, places them on Apache Kafka, and applies them to a PostgreSQL-backed account ledger. The project demonstrates an asynchronous, event-driven payment workflow with request validation, database migrations, idempotency, and dead-letter handling.

> **Project status:** This repository is a learning-oriented foundation, not a production-ready payment processor. The [Known limitations](#known-limitations) section is important before using it as a reference implementation.

## Problem statement

Reward and payment events are often generated by user actions, orders, refunds, or external systems. A synchronous endpoint that performs all database work before responding can:

- keep clients waiting while downstream work completes;
- couple API availability to database availability;
- lose work when a process fails midway through a request;
- process a retried request more than once;
- make traffic spikes expensive to absorb; and
- provide little isolation for malformed or repeatedly failing messages.

The central problem is therefore: **how can a service accept a transaction request quickly and process it reliably without creating duplicate ledger entries?**

## What this project solves

This service provides a small example of the following solution:

1. Validate an incoming transaction at the HTTP boundary.
2. Return `202 Accepted` after publishing a message to Kafka.
3. Consume the message asynchronously.
4. Record the transaction in a PostgreSQL ledger.
5. Update the account balance.
6. Use a unique idempotency key to detect duplicate delivery.
7. Retry consumer failures and route exhausted messages to a dead-letter topic.

The API is intentionally asynchronous: `202 Accepted` means that the request was accepted for processing, not that the balance has already changed.

## Real-life examples

### 1. E-commerce reward redemption

When a customer redeems 50 reward points at checkout, the checkout service can submit a transaction and continue. The rewards service processes the event independently, records the debit, and updates the customer’s reward account.

### 2. Cashback after a purchase

An order service can publish a cashback credit after payment succeeds. Kafka buffers bursts during a sale, while the ledger preserves an auditable record of each account change.

### 3. Refund or compensation workflow

If a payment is cancelled, a compensating transaction can be submitted. The same asynchronous pipeline can process it without requiring the original HTTP request to remain open.

### 4. Retried client requests

Mobile clients and API gateways may retry after a timeout even when the first request reached the server. Supplying the same `Idempotency-Key` lets the consumer recognize the repeated business operation instead of creating another ledger entry.

## Architecture

```text
                HTTP
                 |
                 v
     +-------------------------+
     | TransactionController    |
     | validate request/header  |
     +------------+------------+
                  |
                  v
     +-------------------------+
     | TransactionProducer      |
     | publish txn.requested   |
     +------------+------------+
                  |
                  v
     +-------------------------+
     | Kafka: txn.requested     |
     | 3 partitions             |
     +------------+------------+
                  |
                  v
     +-------------------------+
     | TransactionConsumer      |
     | idempotency + transaction|
     +-----+---------------+---+
           |               |
           v               v
     +-----------+   +-------------+
     | PostgreSQL|   | Kafka DLT   |
     | accounts  |   | after retry |
     | ledger    |   +-------------+
     +-----------+
```

### Main components

- **`TransactionController`**: exposes `POST /transactions`, reads `Idempotency-Key`, and validates the JSON body.
- **`TransactionProducer`**: sends a transaction event to `txn.requested`, using the account ID as the Kafka key.
- **`TransactionConsumer`**: consumes events, inserts a ledger row, and subtracts the amount from the account balance.
- **`KafkaConfig`**: defines the topic, partitions, retry backoff, and dead-letter publishing.
- **Spring Data repositories**: provide persistence access for `Account` and `LedgerEntry`.
- **Flyway migration**: creates the database schema and seeds `acc_123`.

## Request lifecycle

1. A client sends a transaction request with an idempotency key.
2. Bean Validation checks that `accountId` is non-blank and `amount` is at least `0.01`.
3. The producer publishes an event to Kafka.
4. The controller responds with `202 Accepted` and an empty body.
5. The consumer receives the event.
6. The consumer attempts to insert a ledger entry. The database unique constraint protects the idempotency key.
7. For a new entry, the account balance is reduced in the same Spring transaction.
8. A processing exception is retried three times with a one-second fixed delay.
9. If retries are exhausted, Spring Kafka publishes the message to a dead-letter topic.

## Architectural decisions

### Asynchronous HTTP-to-Kafka handoff

The API does not perform ledger work in the request thread. This keeps request latency predictable and allows Kafka to absorb temporary processing spikes.

### Kafka as a durable work boundary

Kafka provides durable, replayable messages and consumer-group coordination. The `rewards-group` consumer group allows the service to scale consumers without every consumer processing every event.

### Account ID as the Kafka key

The producer uses `accountId` as the message key. Kafka keeps messages with the same key in the same partition, which helps preserve per-account ordering. Ordering is not a replacement for database locking or concurrency controls, but it is a useful event-streaming choice.

### PostgreSQL as the system of record

Balances and ledger entries require transactional persistence, constraints, and strong consistency. PostgreSQL is a better fit than using Kafka as the only source of truth for this example.

### Database-enforced idempotency

The `ledger_entries.idempotency_key` column is `UNIQUE NOT NULL`. Enforcing uniqueness in the database is safer than relying only on an in-memory set, which would be lost during restarts and would not work across multiple application instances.

### Flyway migrations

The schema is versioned in source control through `V1__init__schema.sql`. This makes local setup repeatable and gives future schema changes an ordered history.

### Dead-letter topic after bounded retries

The error handler retries transient failures and then publishes an unprocessable event to a dead-letter topic. Bounded retries prevent one poison message from blocking a partition forever.

## Why this approach

| Approach | Benefits | Trade-offs | Decision |
|---|---|---|---|
| Synchronous REST + direct database update | Simple request flow and immediate result | Higher latency, tighter coupling, poor spike handling, difficult retries | Not selected for the primary flow |
| REST + Kafka + PostgreSQL | Decoupled processing, buffering, replayability, scalable consumers, durable ledger | Eventual consistency, operational Kafka cost, more failure modes | Selected |
| Kafka-only state | High throughput and replayable events | Harder balance queries, recovery, constraints, and audit reads | Not selected as the sole store |
| In-memory idempotency cache | Fast duplicate checks | Lost on restart, inconsistent across replicas, unbounded memory concerns | Not sufficient |
| Distributed workflow/orchestration platform | Rich retries and workflow visibility | More infrastructure than this small problem needs | Future option for multi-step workflows |

This is a pragmatic learning architecture: Kafka handles transport and buffering, while PostgreSQL owns business state and constraints. A production system would add an outbox or equivalent delivery guarantee to close the gap between database commits and message publication.

## Data model

### `accounts`

| Column | Meaning |
|---|---|
| `id` | Account identifier and primary key |
| `balance` | Current account balance, stored as `DECIMAL(15, 2)` |

### `ledger_entries`

| Column | Meaning |
|---|---|
| `id` | Database-generated ledger identifier |
| `idempotency_key` | Unique business request key |
| `account_id` | Account affected by the transaction |
| `amount` | Amount debited by the current implementation |
| `created_at` | Time at which the entry was created |

The migration seeds account `acc_123` with a balance of `1000.00`.

## Run locally

### 1. Start infrastructure

```bash
docker compose up -d
```

This starts:

- PostgreSQL at `localhost:5432`
- Kafka at `localhost:9092`

The default local credentials are defined in [`docker-compose.yml`](./docker-compose.yml) and should not be reused outside local development.

### 2. Run the tests

```bash
./mvnw test
```

### 3. Start the application

```bash
./mvnw spring-boot:run
```

Flyway runs the initial migration on startup. The application reads its local connection and Kafka settings from [`application.yml`](./src/main/resources/application.yml).

### 4. Submit a transaction

```bash
curl -i -X POST http://localhost:8080/transactions \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-transaction-001' \
  -d '{"accountId":"acc_123","amount":50.00}'
```

Expected HTTP response:

```text
HTTP/1.1 202 Accepted
```

Use the same idempotency key to model a client retry. The intended consumer behavior is to keep one ledger entry for that business operation.

### 5. Stop infrastructure

```bash
docker compose down
```

Add `-v` only when you intentionally want to remove the local database volume after one is introduced or managed by Docker.

## API reference

### `POST /transactions`

#### Headers

| Header | Required | Description |
|---|---|---|
| `Content-Type` | Yes | Must be `application/json` |
| `Idempotency-Key` | Yes | Stable unique key for the business operation |

#### Request body

```json
{
  "accountId": "acc_123",
  "amount": 50.00
}
```

#### Validation rules

- `accountId` must not be blank.
- `amount` must be present.
- `amount` must be at least `0.01`.

#### Responses

- `202 Accepted`: request was accepted for asynchronous processing.
- `400 Bad Request`: validation failed or a required header/body value is missing.

The current endpoint does not expose a transaction status or result query. A production API would normally return a correlation/transaction ID and provide a status endpoint.

## Reliability and operational concerns

- **Idempotency:** keep the key stable across retries and make it unique per business operation.
- **Ordering:** the account ID key helps preserve partition order, but concurrent consumers and database behavior still require careful design.
- **Money:** `BigDecimal` and PostgreSQL `DECIMAL` avoid binary floating-point rounding; production systems should also define currency and scale explicitly.
- **Retries:** retry only failures likely to recover. Permanent validation or business errors should be classified separately.
- **Dead letters:** monitor the DLT, preserve failure metadata, and provide a safe replay/remediation process.
- **Observability:** add structured logs, correlation IDs, Kafka lag metrics, processing latency, and database failure metrics.
- **Security:** use secrets management, TLS/SASL for Kafka, database least privilege, authentication, authorization, and request rate limits.
- **Concurrency:** protect against concurrent updates and define behavior for insufficient funds or negative balances.
- **Delivery guarantees:** consider an outbox pattern, transactional Kafka publishing, or a workflow coordinator where atomic database-and-message behavior is required.

## Known limitations

These are deliberately recorded so the documentation remains faithful to the current source:

1. **Producer/consumer payload mismatch:** `TransactionProducer` currently publishes a map containing `idempotencyKey` and a nested `transactionRequest`. `TransactionConsumer` currently reads `accountId` and `amount` as top-level map fields. The event contract should be aligned before relying on end-to-end processing.
2. **No result tracking endpoint:** the API accepts work but does not expose a transaction ID or processing status.
3. **No balance guard:** the consumer subtracts the amount without checking available balance or preventing an invalid negative balance.
4. **No explicit database locking:** concurrent transactions for one account need a defined locking or optimistic-versioning strategy.
5. **No outbox:** a production-grade design should address the possibility of a process failure around message publication and persistence.
6. **Development configuration:** credentials, localhost endpoints, permissive JSON trusted packages, and plaintext Kafka are suitable only for local learning.
7. **Poison-pill branch:** the consumer contains an intentional `poison_pill` account ID path for exercising failure and DLT behavior.

## Recommended next steps

1. Introduce a typed `TransactionEvent` shared by producer and consumer.
2. Return a transaction/correlation ID and add `GET /transactions/{id}`.
3. Add explicit debit/credit semantics, currency, and balance validation.
4. Add a unique constraint mapping and integration tests for duplicate delivery.
5. Add optimistic locking or a database-side atomic balance update.
6. Add an outbox table and publisher for reliable event publication.
7. Add authentication, authorization, secret injection, and TLS.
8. Add metrics, structured logging, tracing, and DLT monitoring.
9. Use Testcontainers for PostgreSQL and Kafka integration tests.
